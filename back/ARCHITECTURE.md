# Архитектура бэкенда

Набросок под задачу «Автоматическая разметка действий по видео». Контракт — в
[`../spec/openapi.yaml`](../spec/openapi.yaml), разбор прозой — в
[`../spec/api.md`](../spec/api.md). Здесь то, как сервис устроен внутри и почему так.

Документ описывает то, что написано и работает: полный путь загрузка → разметка →
правки → выгрузка прогнан на восемнадцати роликах эталона. Где решение стоило
ошибки в рантайме, это сказано прямо — такие места переживают рефакторинг хуже
всего.

---

## Что считает разметку

**Marlin-2B одним проходом.** Ролик на вход — перечисление событий с таймкодами на
выход. Отдельного этапа поиска границ нет.

Где она считается — параметр конфигурации, а не свойство архитектуры: на своей
машине или в облаке, см. «Провайдеры инференса».

Модель выбрана потому, что она единственная из рассмотренных обучена именно на
перечисление событий с таймкодами, а не на moment retrieval — то есть отвечает на вопрос
«из каких шагов состоит ролик», а не «где в ролике вот это». Родной режим — 2 fps и
caption-промпт `Describe the video with a scene summary and timestamped events`; в этом
режиме её и гоняем, потому что на нём она обучалась.

У этого выбора есть цена, и она видна в архитектуре: **Marlin не разделяет глагол и
объект**, а возвращает описание одной строкой. Кейс требует их раздельно и меряет обе
колонки. Поэтому за инференсом идёт короткий текстовый проход через языковую модель — стадия
`structure`. Видео он не видит.

## Общая схема

```
                         ┌ docker compose ─────────────────────────┐
   браузер               │                                         │
      │ HTTP / SSE       │                                         │
      ▼                  │                                         │
┌───────────┐  прогресс  │  ┌──────────┐        ┌──────────┐       │
│    api    │◀───────────┼──│  redis   │◀───────│  worker  │       │
│  FastAPI  │            │  │  pubsub  │        │ CPU-only │       │
└─────┬─────┘            │  └──────────┘        └────┬─────┘       │
      │                  │                           │             │
      │   ┌──────────────┼───────────────────────────┘             │
      ▼   ▼              │             │             │             │
┌───────────┐  ┌─────────┴─┐           │             │             │
│ postgres  │  │  /data    │           │             │             │
│ данные +  │  │ видео,    │           │             │             │
│  очередь  │  │ кадры     │           │             │             │
└───────────┘  └───────────┘           │             │             │
                         └─────────────┼─────────────┼─────────────┘
                                       │ ролик       │ 6–10 строк
                                       ▼             ▼
                            ┌─────────────────┐  ┌─────────────┐
                            │   Marlin-2B     │  │  языковая   │
                            │ хост (MPS) или  │  │   модель    │
                            │  Modal (A10G)   │  │ (structure) │
                            └─────────────────┘  └─────────────┘
```

**Зрительная модель живёт вне контейнеров.** Docker на macOS запускает контейнеры в
виртуальной машине, а она не отдаёт наружу ускоритель Apple — модель на MPS обязана
считаться на хосте, и воркер ходит к ней по HTTP на `host.docker.internal`, ровно так
же, как ходил бы к облачному провайдеру. Сервис обязан слушать `0.0.0.0`: на loopback
контейнер не достучится, и выглядит это как «connection refused», а не как таймаут.

На машине с NVIDIA этой оговорки нет, но интерфейс всё равно один: воркеру безразлично,
кто отвечает.

## Четыре процесса

**`api`** — FastAPI под uvicorn. HTTP, валидация, БД, файлы, раздача SSE. Ничего тяжёлого
не считает и никуда не ходит надолго.

**`worker`** — обычный CPU-контейнер. Берёт задачи из очереди, гоняет стадии, публикует
прогресс. Ему не нужен GPU, потому что инференс уехал на Modal; из тяжёлого у него только
`ffmpeg` для ключевых кадров.

**`postgres`** — ролики, задачи, разметки, сегменты.

**`redis`** — очередь задач и канал прогресса.

Почему воркер отдельно, а не `BackgroundTasks` внутри `api`: задача живёт до двух минут.
Внутри веб-процесса это означает, что рестарт api убивает работу пользователя, а отмена и
повтор превращаются в самодельный планировщик. Отдельный процесс с очередью даёт всё это
даром, а стоит одного контейнера.

**Очередь — сама таблица `jobs`**, через `SELECT ... FOR UPDATE SKIP LOCKED`. Строка
задачи и так лежит в Postgres; отдельный брокер был бы вторым источником истины про один
и тот же статус, который пришлось бы синхронизировать.

Redis остаётся **каналом прогресса**: воркер шлёт события в `job:{id}`, `api` на них
подписан и ретранслирует в SSE. Опрос при этом читает таблицу и живёт полностью
независимо — если redis отвалится, деградирует только поток событий, а не обработка.

## Стадии задачи

| Стадия | Что делает | Где считается | Чем ломается |
|---|---|---|---|
| `submit` | Читает файл, отправляет вызов на Modal, сохраняет `FunctionCall.object_id` | worker | Modal недоступен, размер запроса |
| `infer` | Marlin смотрит ролик на 2 fps и пишет события с таймкодами | Modal, GPU | Холодный старт, таймаут, OOM |
| `parse` | Разбор ответа в `Annotation` | worker | Модель ответила прозой без таймкодов |
| `structure` | Делит описание на `action` / `object` / `tool`, ставит `confidence` | LLM API | Лимиты, отказ схемы, баланс |
| `postprocess` | Сортировка, клиппинг по длительности, отсев коротышей, слияние дублей | worker | — |
| `keyframes` | Выбор и нарезка ключевых кадров | worker, ffmpeg | Битый файл |
| `persist` | Запись разметки и метрик прогона | worker | — |

Стадии видны наружу: `GET /jobs/{id}` отдаёт `stage`, `stage_index`, `stages[]` и
`timings` по каждой. `timings` — не отладка, а прямой замер требования «не более 2 минут
на ролик».

**Прогресс внутри `infer` — оценка, а не измерение.** Modal возвращает результат вызова
целиком; промежуточного прогресса у нас нет. Число считается по медиане прошлых прогонов
на этом же типе GPU, и в `api.md` это сказано прямо, чтобы интерфейс не подавал его как
точное.

### `parse`

Переиспользует `hyp0/parse.py` целиком: `from_marlin` для caption-режима, `from_json` для
запасного, `auto` — попытка обоих. Вместе с ним переезжает и его правило: **провал разбора
не равен провалу модели**. В API это отдельный код `model_parse_failed`, а сырой текст
доступен по `GET /jobs/{id}/raw` — он сохраняется всегда, даже когда разбор упал.

### `structure`

Вход — 6–10 коротких строк вроде «берёт кружку». Выход — те же строки, разложенные на
поля. Три решения:

- **Одним запросом на весь ролик**, а не по строке на запрос. Модель видит соседние шаги
  и держит формулировки однообразными, а узкий разброс формы прямо повышает шанс
  совпадения с таргетом при оценке.
- **Structured output** (`response_format` со схемой), а не разбор текста регуляркой.
  Схема фиксирована, и невалидный ответ должен быть ошибкой, а не поводом угадывать.
- **Словарь ролика вместо свободных строк.** Модель сначала объявляет `actions`,
  `objects`, `tools` ролика, а шаги ссылаются на них индексами. Просьба «пиши
  единообразно» не работает: на первом же прогоне один предмет получил три имени —
  «yellow toy car», «toy car front», «toy car», — а один и тот же компонент два.
  Со словарём вариантов написания просто нет: 5 названий предметов схлопнулись в 3,
  ровно как в эталоне. С действиями приём пока не сработал — модель по-прежнему даёт
  своё действие каждому шагу, тогда как эталон переиспользует. Стоит это лишних токенов
  на выходе (595 -> 1038 на ролике из шести шагов).
- **Кэш стабильного префикса.** Инструкция, критерий гранулярности (дословно из
  `hyp0/prompt.py`) и описание формата не меняются между роликами — они помечаются
  точкой кэширования, а переменная часть (строки ролика) идёт после.

**Провайдер — параметр конфигурации, а не имя в коде.** Нужен любой OpenAI-совместимый
эндпоинт: `LLM_BASE_URL`, `LLM_API_KEY`, `STRUCTURE_MODEL`. В Python это клиент `openai` с
подменённым `base_url` — отдельного SDK не нужно. Сейчас настроен Groq
(`https://api.groq.com/openai/v1`); до него был OpenRouter, а до него — прямой вызов
Anthropic. Смена провайдера за сессию произошла дважды, и именно поэтому его имя
нигде не зашито: это правка `.env`, а не рефакторинг.

Что из этого следует и о чём надо помнить:

- **Имя модели берётся из каталога провайдера** (`GET {LLM_BASE_URL}/models`), а не по
  памяти: у каждого своя схема именования, и один и тот же Claude называется
  `claude-haiku-4-5` у Anthropic и `anthropic/claude-haiku-4.5` у OpenRouter.
- **Structured output и кэш промпта — свойства конкретной модели у конкретного
  провайдера**, а не гарантия протокола. Проверять по первому же прогону и полю `usage`,
  а не по документации.
- **`max_tokens` обязателен.** Без него провайдер резервирует максимум модели и может
  отказать по балансу, хотя ответ здесь — пара сотен токенов.

Задача стадии узкая: разложить короткую фразу по трём полям. Поэтому модель выбирается
ценой, и сравнить кандидата — это смена одной переменной, а не новая интеграция.

Критерий гранулярности обязан совпадать в трёх местах: инструкция разметчику, промпт
модели, пороги постобработки. Разойдутся — метрика начнёт мерить рассогласование между
ними, а не качество разметки. Источник один: `hyp0/prompt.py`.

### `postprocess`

- клиппинг границ в `[0, duration_s]` и отсев вырожденных шагов — уже есть в `parse.py`;
- шаги короче `MIN_SEGMENT_S` схлопываются с соседом;
- соседние шаги с почти одинаковым описанием **предлагаются** к слиянию, а не сливаются
  молча: пересегментация — частая ошибка, но склеить два разных шага хуже, чем оставить
  лишнюю границу, которую пользователь уберёт одним жестом.

Порог осторожности здесь не из вкуса. В `hyp0` замерено, что равномерное разбиение даёт
boundary F1 = 0.59 даром — то есть недосегментация умеет выглядеть приличным числом.
Агрессивная склейка улучшит метрику и ухудшит продукт.

### `keyframes`

Прежнее правило («кадр с минимальной временной разностью признаков») опиралось на кривую,
которую считал отдельный этап сегментации. Его больше нет, и правило пришлось
переизобрести.

Новое: внутри `[start + 10 %, end − 10 %]` берётся кадр с максимальной резкостью
(дисперсия лапласиана) со штрафом за большое отличие от соседних кадров. Первое отсекает
смазанные кадры, второе — переходные, где действие ещё меняется. Отступ от границ убирает
кадры стыка. Считается на декодированных кадрах через OpenCV, модели не требует.

## Провайдеры инференса

Зрительная модель может считаться на своей машине или в облаке. Выбор — строка
конфигурации `INFERENCE_PROVIDERS`, список через запятую в порядке предпочтения;
отвечает первый, кто справился, а переход на запасного записывается в задачу.

Это не запас прочности ради красоты. Лимит трат Modal на расчётный период однажды
остановил обработку целиком: задачи падали в `inference_failed`, продукт стоял, и
починить это со своей стороны было нечем. Провайдер, зашитый в код, — это чужой биллинг
в роли единственной точки отказа.

Интерфейс у обоих один: `annotate(video_bytes, fps, max_new_tokens, suffix)` → сырой
текст, способ сборки входа, имя устройства и тайминги. Кто именно посчитал, видно в
`job.cost` — по этому же полю считается стоимость прогона.

### `local` — на своей машине

`local_app/serve.py`, запускается вне `docker compose` (`uvicorn`, порт 8100). Модель
грузится один раз на старте сервиса, а не по первому запросу: иначе первый ролик
пользователя оплачивает загрузку и выглядит как зависшая обработка.

Ролик уходит сырыми байтами в теле POST — сеть здесь локальная, раздувать десять
мегабайт в base64 незачем.

Замер на M4 Pro (MPS, bf16): загрузка модели 11 с однократно, дальше 26–30 с на ролик.
Вдвое медленнее A10G, но по сумме для демонстрации выигрышнее: модель всегда тёплая,
тогда как в облаке каждый холодный старт добавлял тридцать секунд и требовал платного
контейнера в простое.

### `modal` — в облаке

`modal_app/marlin.py` — отдельное приложение, деплоится своим циклом (`modal deploy`), в
`docker compose` не входит. Каталог назван `modal_app`, а не `modal`, намеренно: пакет с
именем `modal` рядом с кодом затеняет сам клиент Modal, и `import modal` внутри файла
ломается при запуске из `back/`.

- Класс с `@modal.enter()`, который грузит `NemoStation/Marlin-2B` один раз на контейнер,
  и методом `annotate(video_bytes, fps, max_new_tokens, prompt)` → сырой текст плюс
  тайминги.
- **Веса — в образ или в Modal Volume**, не скачиванием из Hugging Face на старте.
  Иначе холодный старт включает загрузку нескольких гигабайт.
- **Тёплый контейнер на время демо.** Загрузка модели занимает десятки секунд, а бюджет —
  120. Холодный старт съедает заметную его часть, поэтому на демо держим минимум один
  экземпляр.
- Ролик уходит **байтами прямо в вызов**: 5–30 с, 720p — единицы-десятки мегабайт.
  Локальный бэкенд не имеет публичного адреса, поэтому вариант «Modal скачает по ссылке»
  отпадает сразу. Упрёмся в лимит запроса — запасной путь Modal Volume.
- Воркер вызывает `spawn`, кладёт идентификатор вызова в строку задачи и опрашивает
  результат. Так задача переживает рестарт воркера, а HTTP-соединение никого не ждёт.
- Репозиторий модели помечен `custom_code` и требует `trust_remote_code`. Совместимость с
  vLLM по-прежнему не проверена — от неё зависит режим `prompt_mode: json` со structured
  output; caption-режим её не требует и работает.
- **`torchvision` обязателен в образе.** Marlin построена на Qwen3-VL, и её
  `Qwen3VLVideoProcessor` импортирует torchvision на этапе загрузки процессора. Без него
  контейнер уходит в crash-loop с `ImportError`, до GPU дело не доходит.

### Что измерено на первом живом прогоне

Ролик `asm_static_00.mp4` (20 с, 720p, 9.7 МБ), A10G, холодный контейнер:

| Что | Секунд |
|---|---|
| Подготовка входа (декодирование на 2 fps) | 1.2 |
| Генерация | 15.1 |
| Итого на GPU | 16.2 |
| Полное время с локальной стороны | 45.5 |

Разница между 16 и 45 секундами — холодный старт: подъём контейнера и загрузка весов из
тома. При бюджете 120 секунд запас есть даже так; на демо тёплый контейнер убирает эти
30 секунд, но стоит денег в простое.

Из трёх вариантов сборки входа сработал первый — `apply_chat_template` с
`video_load_backend="torchcodec"`. Перебор в `_build_inputs` оставлен: он ничего не стоит,
а при смене версии transformers снова окажется полезен.

Формат ответа — ровно тот, что ждёт `hyp0/parse.py::from_marlin`: абзац `Scene:` и строки
`<начало - конец> описание`. Парсер разобрал ответ без правок, 6 шагов на 20 секунд.

Имена параметров сверены с установленным клиентом (modal 1.5.5): `min_containers`,
`scaledown_window`, `modal.Cls.from_name`. В более ранних версиях они назывались иначе
(`keep_warm`, `container_idle_timeout`, `Cls.lookup`) — при обновлении клиента проверить
заново.

Порядок первого запуска важен: `modal deploy`, затем однократный `download_weights`, и
только потом инференс. Иначе веса поедут в том на первом же боевом вызове и холодный старт
съест бюджет ролика.

## Раскладка

```
back/
  app/
    main.py            сборка FastAPI, роутеры, CORS, обработчики ошибок
    api/v1/            videos.py jobs.py annotations.py export.py service.py common.py
    schemas.py         pydantic-модели тел запросов
    serializers.py     форма ответов; она же источник правды для spec/openapi.yaml
    domain.py          Segment / Annotation — перенос hyp0/schema.py
    services.py        инварианты разметки, производные поля, экспорт
    models.py          SQLAlchemy
    storage.py         медиа и кэш кадров за интерфейсом
    events.py          redis pub/sub → SSE
    db.py              движок, сессия, создание схемы
    config.py          pydantic-settings
  worker/
    main.py            цикл выборки задач, стадии, публикация прогресса
    inference.py       выбор провайдера зрительной модели
    local_client.py    модель на хосте (HTTP)
    modal_client.py    модель в облаке
    parse.py           разбор ответа модели
    structure.py       стадия structure: деление описания на поля
    keyframe.py        выбор ключевого кадра
  local_app/
    serve.py           зрительная модель на хосте (запускается вне контейнеров)
  modal_app/
    marlin.py          она же в облаке (деплоится отдельно)
  migrations/init/     расширения Postgres
```

Модули плоские, а не пакеты. Слоёв здесь на пару сотен строк каждый, и каталог с одним
файлом внутри — это оглавление к оглавлению. Разрастётся — разложить недолго.

**Чего нет и почему это заметно.** Нет `tests/`: под требование «100 % валидности
экспорта» нужен хотя бы тест «выгрузка против схемы», и его отсутствие — долг, а не
решение. Нет alembic — см. «Модель данных», там же цена этого решения.

`domain.py` — перенос `hyp0/schema.py` как есть, а не новая модель. Там уже написаны
проверка `end_s < start_s`, `boundaries(internal_only=…)` и канонический `text()`, и на
них уже опираются метрики. Своя параллельная модель означала бы два формата, которые
однажды разойдутся.

`storage.py` держит файловое хранилище за интерфейсом: на сегодня это общий том `/data`,
завтра — S3, и подмена не должна расползаться по сервисам.

## Модель данных

```
videos      id · sha256(uniq) · filename · mime · duration_s · fps · width · height
            size_bytes · storage_path · created_at

jobs        id · video_id → videos · status · stage · progress · params(jsonb)
            model · structure_model · modal_call_id · raw_path
            timings(jsonb) · cost(jsonb) · error(jsonb)
            created_at · started_at · finished_at
            uniq (video_id, params_hash) частичный — под идемпотентность

annotations id · video_id → videos · job_id → jobs · version · model · meta(jsonb)
            created_at · updated_at

segments    id · annotation_id → annotations · index · start_s · end_s
            action · object · tool · confidence · keyframe_ts · edited_by_human
            uniq (annotation_id, index)
```

**Сегменты строками, а не jsonb-блобом.** `edited_by_human` — продуктовая метрика: она
отвечает на вопрос, какая доля автоматической разметки уходит без правок, то есть прямо
измеряет пользу системы. Считать её надо запросом по шагам, а не разбором json в
приложении.

**Непересечение шагов снимаем в базу.** Раз Postgres, пусть перекрытие будет невозможно
физически:

```sql
ALTER TABLE segments ADD CONSTRAINT segments_no_overlap
  EXCLUDE USING gist (
    annotation_id WITH =,
    numrange(start_s::numeric, end_s::numeric) WITH &&
  );
```

Требует `btree_gist`. Сервисный слой всё равно проверяет и отдаёт понятный `422` с кодом
`segment_overlap` — ограничение базы это последний рубеж, а не сообщение пользователю.

Две детали, без которых это не работает; обе выяснились на живых запросах.

**Оба ограничения — `DEFERRABLE INITIALLY DEFERRED`.** Любая перестановка шагов (правка
границы, `split`, `merge`, удаление) на время транзакции нарушает и уникальность
`(annotation_id, index)`, и непересечение: шагу присваивается индекс, который в этот
момент ещё занят соседом. Корректно состояние только к коммиту, и проверять надо там.
С немедленной проверкой `split` падал на ровном месте.

**`autoflush=False` у сессии.** Иначе любой запрос внутри обработчика (например, чтение
ролика ради длительности) сбрасывает незакоммиченную правку в базу, ограничение
срабатывает раньше сервисной проверки, и пользователь получает `500` вместо внятного
`422` с указателем на поле. Плюс глобальный обработчик `IntegrityError` — если
ограничение всё-таки сработало, наружу уходит `422`, а не сбой сервиса.

Миграций нет: схема создаётся `Base.metadata.create_all` плюс сырой DDL для расширения и
ограничений. Для хакатона alembic — лишний слой, но это решение уже стоило одного отказа
в рантайне: **`create_all` создаёт недостающие таблицы, но не колонки**, и добавленное в
модель поле на живой базе молча не появилось — запись упала на `persist`. Пока alembic
нет, догоняющие правки схемы лежат явным списком в `init_db()`. Разрастётся до трёх-четырёх
строк — заводить миграции, а не продолжать список.

`annotations.version` — оптимистичная блокировка под `ETag` / `If-Match`. Истории версий
нет: это осознанное ограничение скоупа, а не забытая функция.

## Экспорт

Формат — канонический, из `hyp0/schema.py`, описан схемой
[`../spec/annotation.schema.json`](../spec/annotation.schema.json). Производные поля API
(`annotation_id`, `version`, `index`, `needs_review`) в выгрузку не попадают: смысл в том,
чтобы выгрузку можно было скормить `hyp0/metrics.py` без конвертера и мерить ровно то, что
уехало пользователю.

Валидация по схеме идёт **перед** отдачей. Не прошло — `500` с кодом
`export_schema_invalid` и списком нарушений, файла пользователь не получает. Требование
«100 % корректности формата» держится этой конструкцией, а не аккуратностью: невалидный
файл физически не может выйти наружу.

Схема отдаётся наружу (`GET /schema/annotation.json`), чтобы у потребителей была та же
копия, а не своя.

## Стоимость

`jobs.cost` заполняется по факту прогона, а не оценкой, и ключ в нём — имя того
провайдера, который реально посчитал. Это ровно те сервисы, которые кейс требует назвать
вместе со стоимостью обработки.

| Сервис | За что платим | Замер на ролик |
|---|---|---|
| Marlin-2B на своей машине | ничего | 26–30 с на MPS (M4 Pro) |
| Marlin-2B на Modal | GPU-секунды на `infer` | 16 с на A10G плюс 30 с холодного старта; тариф — из биллинга под выбранную карту |
| Языковая модель (сейчас Groq) | стадия `structure` | ≈700 входных и 1300 выходных токенов |

Расход токенов **зависит от модели**, а не только от ролика. Замеры на шести шагах:
`openai/gpt-oss-120b` через Groq — 529/595 на плоской схеме и около 700/1300 после
перехода на словарь ролика; тот же ролик на Claude давал 708/205. Число надо переснимать
при каждой смене модели, а цену за токены брать из тарифов провайдера.

Тариф Modal в таблицу не вписан намеренно: он зависит от типа карты, а выдумывать цифру,
которую нечем подтвердить, — плохой способ закрыть графу в защите. GPU-секунды при этом
пишутся в задачу, так что умножить их на тариф можно в любой момент.

## Конфигурация

Всё через переменные окружения, см. [`.env.example`](.env.example). Обязательные:
`DATABASE_URL`, `REDIS_URL`, `MEDIA_ROOT`, `LLM_API_KEY`. Токены Modal нужны только
если он есть в `INFERENCE_PROVIDERS`.

Ключи живут только в `.env`, который лежит в `.gitignore`. В репозиторий коммитится
`.env.example` с пустыми значениями.

Значения, которые задают поведение продукта, а не инфраструктуру, и потому подбираются
замером: `MARLIN_FPS` (2.0 — родная частота модели), `CONFIDENCE_THRESHOLD`,
`MIN_SEGMENT_S`, `MERGE_THRESHOLD`, `STRUCTURE_MODEL`.

Сервис не стартует с пустыми обязательными ключами: лучше упасть на старте, чем принять
ролик и упасть на стадии `structure`.

## Развёртывание

Полная инструкция — в [`../README.md`](../README.md). Коротко, для локального пути:

```bash
cp back/.env.example back/.env                        # вписать LLM_API_KEY
# зрительная модель на хосте: вне контейнеров и обязательно на 0.0.0.0
cd back && HF_HUB_CACHE=../../hf_cache/hub PYTORCH_ENABLE_MPS_FALLBACK=1 \
  ../../venv/bin/python -m uvicorn local_app.serve:app --host 0.0.0.0 --port 8100
docker compose -f back/docker-compose.yml up -d
```

Для облачного пути вместо сервиса на хосте — `modal deploy back/modal_app/marlin.py`
и `INFERENCE_PROVIDERS=modal` в `.env`.

`GET /health` проверяет ровно то, что настроено: перечисляет провайдеров из
`INFERENCE_PROVIDERS` и говорит про каждого, готов ли он. Достаточно одного рабочего —
список и заведён затем, чтобы отказ любого не останавливал обработку.

## Чего здесь осознанно нет

- **Аутентификации, ролей, биллинга** — вынесено кейсом. В спецификации это записано явно
  (`security: []`), чтобы читалось как решение, а не как пропуск.
- **Пакетной обработки.** Ролики по одному; очередь готова, но API загрузки пачкой нет.
- **Истории версий и отката.**
- **Горизонтального масштабирования.** Один воркер, одна очередь. Промышленная нагрузка
  вне скоупа, а один воркер делает время обработки измеримым.
- **Кэша ответов модели между роликами.** Дедупликация по sha256 закрывает практический
  случай — повторную загрузку того же файла на демо.
