# Архитектура бэкенда

Набросок под задачу «Автоматическая разметка действий по видео». Контракт — в
[`../spec/openapi.yaml`](../spec/openapi.yaml), разбор прозой — в
[`../spec/api.md`](../spec/api.md). Здесь то, как сервис устроен внутри и почему так.

Кода приложения ещё нет: этот документ и `docker-compose.yml` описывают то, что будет
написано, и фиксируют решения до того, как они разъедутся по трём головам.

---

## Что считает разметку

**Marlin-2B на Modal, одним проходом.** Ролик на вход — перечисление событий с таймкодами
на выход. Отдельного этапа поиска границ нет.

Модель выбрана потому, что она единственная из рассмотренных обучена именно на
перечисление событий с таймкодами, а не на moment retrieval — то есть отвечает на вопрос
«из каких шагов состоит ролик», а не «где в ролике вот это». Родной режим — 2 fps и
caption-промпт `Describe the video with a scene summary and timestamped events`; в этом
режиме её и гоняем, потому что на нём она обучалась.

У этого выбора есть цена, и она видна в архитектуре: **Marlin не разделяет глагол и
объект**, а возвращает описание одной строкой. Кейс требует их раздельно и меряет обе
колонки. Поэтому за инференсом идёт короткий текстовый проход через Claude — стадия
`structure`. Видео он не видит.

## Общая схема

```
   браузер
      │ HTTP / SSE
      ▼
┌───────────┐   задача   ┌──────────┐        ┌──────────┐  spawn/poll  ┌─────────────┐
│    api    │───────────▶│  redis   │◀───────│  worker  │─────────────▶│    Modal    │
│  FastAPI  │◀───────────│ очередь  │        │ CPU-only │              │  Marlin-2B  │
└─────┬─────┘  прогресс  │ + pubsub │        └────┬─────┘◀─────────────│   на GPU    │
      │                  └──────────┘             │   сырой текст      └─────────────┘
      │                                           │
      │                                           └────────────▶ OpenRouter (structure)
      └────────────┬──────────────────────────────┘
                   ▼                      ▼
             ┌───────────┐          ┌───────────┐
             │ postgres  │          │  /data    │  видео, кэш кадров, ключевые кадры
             └───────────┘          └───────────┘
```

Раз модель живёт на Modal, локально GPU не нужна нигде. Побочное следствие приятное: весь
стек ложится в один `docker compose` без GPU-runtime и без оговорки про то, что Docker на
macOS не пробрасывает MPS — на маке разработчика всё работает так же, как на сервере.

## Четыре процесса

**`api`** — FastAPI под uvicorn. HTTP, валидация, БД, файлы, раздача SSE. Ничего тяжёлого
не считает и никуда не ходит надолго.

**`worker`** — обычный CPU-контейнер. Берёт задачи из очереди, гоняет стадии, публикует
прогресс. Ему не нужен GPU, потому что инференс уехал на Modal; из тяжёлого у него только
`ffmpeg` для ключевых кадров.

**`postgres`** — ролики, задачи, разметки, сегменты.

**`redis`** — очередь задач и канал прогресса.

Почему воркер отдельно, а не `BackgroundTasks` внутри `api`: задача живёт до двух минут.
Внутри веб-процесса это означает, что рестарт api убивает работу пользователя, а отмена и
повтор превращаются в самодельный планировщик. Отдельный процесс с очередью даёт всё это
даром, а стоит одного контейнера.

Почему redis, а не только Postgres как очередь: нужен не столько брокер, сколько **канал
публикации прогресса**. Воркер шлёт события в `job:{id}`, `api` на них подписан и
ретранслирует в SSE. Опрос при этом читает таблицу `jobs` и живёт полностью независимо —
если redis отвалится, деградирует только поток событий, а не обработка.

## Стадии задачи

| Стадия | Что делает | Где считается | Чем ломается |
|---|---|---|---|
| `submit` | Читает файл, отправляет вызов на Modal, сохраняет `FunctionCall.object_id` | worker | Modal недоступен, размер запроса |
| `infer` | Marlin смотрит ролик на 2 fps и пишет события с таймкодами | Modal, GPU | Холодный старт, таймаут, OOM |
| `parse` | Разбор ответа в `Annotation` | worker | Модель ответила прозой без таймкодов |
| `structure` | Делит описание на `action` / `object` / `tool`, ставит `confidence` | OpenRouter | Лимиты, отказ схемы, смена апстрим-провайдера |
| `postprocess` | Сортировка, клиппинг по длительности, отсев коротышей, слияние дублей | worker | — |
| `keyframes` | Выбор и нарезка ключевых кадров | worker, ffmpeg | Битый файл |
| `persist` | Запись разметки и метрик прогона | worker | — |

Стадии видны наружу: `GET /jobs/{id}` отдаёт `stage`, `stage_index`, `stages[]` и
`timings` по каждой. `timings` — не отладка, а прямой замер требования «не более 2 минут
на ролик».

**Прогресс внутри `infer` — оценка, а не измерение.** Modal возвращает результат вызова
целиком; промежуточного прогресса у нас нет. Число считается по медиане прошлых прогонов
на этом же типе GPU, и в `api.md` это сказано прямо, чтобы интерфейс не подавал его как
точное.

### `parse`

Переиспользует `hyp0/parse.py` целиком: `from_marlin` для caption-режима, `from_json` для
запасного, `auto` — попытка обоих. Вместе с ним переезжает и его правило: **провал разбора
не равен провалу модели**. В API это отдельный код `model_parse_failed`, а сырой текст
доступен по `GET /jobs/{id}/raw` — он сохраняется всегда, даже когда разбор упал.

### `structure`

Вход — 6–10 коротких строк вроде «берёт кружку». Выход — те же строки, разложенные на
поля. Три решения:

- **Одним запросом на весь ролик**, а не по строке на запрос. Модель видит соседние шаги
  и держит формулировки однообразными, а узкий разброс формы прямо повышает шанс
  совпадения с таргетом при оценке.
- **Structured output** (`response_format` со схемой), а не разбор текста регуляркой.
  Схема фиксирована, и невалидный ответ должен быть ошибкой, а не поводом угадывать.
- **Кэш стабильного префикса.** Инструкция, критерий гранулярности (дословно из
  `hyp0/prompt.py`) и описание формата не меняются между роликами — они помечаются
  точкой кэширования, а переменная часть (строки ролика) идёт после.

**Вызов идёт через OpenRouter**, а не напрямую к провайдеру модели: OpenAI-совместимый
`POST https://openrouter.ai/api/v1/chat/completions`, ключ в `Authorization: Bearer`.
В Python это клиент `openai` с подменённым `base_url` — отдельного SDK не нужно.

Что из этого следует и о чём надо помнить:

- **Модель называется слагом с префиксом провайдера**: `anthropic/claude-haiku-4.5`, а не
  `claude-haiku-4-5`. Список слагов — `GET /api/v1/models`, оттуда же цены; выдумывать
  идентификатор по памяти нельзя, он не совпадёт.
- **Апстрим-провайдер может подмениться.** OpenRouter маршрутизирует запрос между
  провайдерами одной модели, а они отличаются поддержкой structured output и кэша. Если
  ответ вдруг перестал держать схему, дело может быть не в промпте. Лечится настройкой
  маршрутизации: требовать поддержку переданных параметров и при необходимости
  прибивать провайдера явно.
- **Кэш и structured output — свойства связки «модель + провайдер»**, а не самого
  OpenRouter. Проверять по полю `usage` первого же прогона, а не по документации.

Модель по умолчанию — `anthropic/claude-haiku-4.5`. Задача узкая: разложить короткую
русскую фразу по трём полям. Это выбор ценой, и он вынесен в конфиг: `STRUCTURE_MODEL`
подставляет `anthropic/claude-sonnet-5` или что угодно ещё из каталога без правок кода.
Если на замере окажется, что модель путает объект с инструментом — переключается
переменной, а не рефакторингом. Это же главный практический выигрыш от OpenRouter:
сравнить пять моделей на этой стадии стоит пяти запусков с разным значением переменной,
а не пяти интеграций.

Критерий гранулярности обязан совпадать в трёх местах: инструкция разметчику, промпт
модели, пороги постобработки. Разойдутся — метрика начнёт мерить рассогласование между
ними, а не качество разметки. Источник один: `hyp0/prompt.py`.

### `postprocess`

- клиппинг границ в `[0, duration_s]` и отсев вырожденных шагов — уже есть в `parse.py`;
- шаги короче `MIN_SEGMENT_S` схлопываются с соседом;
- соседние шаги с почти одинаковым описанием **предлагаются** к слиянию, а не сливаются
  молча: пересегментация — частая ошибка, но склеить два разных шага хуже, чем оставить
  лишнюю границу, которую пользователь уберёт одним жестом.

Порог осторожности здесь не из вкуса. В `hyp0` замерено, что равномерное разбиение даёт
boundary F1 = 0.59 даром — то есть недосегментация умеет выглядеть приличным числом.
Агрессивная склейка улучшит метрику и ухудшит продукт.

### `keyframes`

Прежнее правило («кадр с минимальной временной разностью признаков») опиралось на кривую,
которую считал отдельный этап сегментации. Его больше нет, и правило пришлось
переизобрести.

Новое: внутри `[start + 10 %, end − 10 %]` берётся кадр с максимальной резкостью
(дисперсия лапласиана) со штрафом за большое отличие от соседних кадров. Первое отсекает
смазанные кадры, второе — переходные, где действие ещё меняется. Отступ от границ убирает
кадры стыка. Считается на декодированных кадрах через OpenCV, модели не требует.

## Modal

`modal_app/marlin.py` — отдельное приложение, деплоится своим циклом (`modal deploy`), в
`docker compose` не входит. Каталог назван `modal_app`, а не `modal`, намеренно: пакет с
именем `modal` рядом с кодом затеняет сам клиент Modal, и `import modal` внутри файла
ломается при запуске из `back/`.

- Класс с `@modal.enter()`, который грузит `NemoStation/Marlin-2B` один раз на контейнер,
  и методом `annotate(video_bytes, fps, max_new_tokens, prompt)` → сырой текст плюс
  тайминги.
- **Веса — в образ или в Modal Volume**, не скачиванием из Hugging Face на старте.
  Иначе холодный старт включает загрузку нескольких гигабайт.
- **Тёплый контейнер на время демо.** Загрузка модели занимает десятки секунд, а бюджет —
  120. Холодный старт съедает заметную его часть, поэтому на демо держим минимум один
  экземпляр.
- Ролик уходит **байтами прямо в вызов**: 5–30 с, 720p — единицы-десятки мегабайт.
  Локальный бэкенд не имеет публичного адреса, поэтому вариант «Modal скачает по ссылке»
  отпадает сразу. Упрёмся в лимит запроса — запасной путь Modal Volume.
- Воркер вызывает `spawn`, кладёт идентификатор вызова в строку задачи и опрашивает
  результат. Так задача переживает рестарт воркера, а HTTP-соединение никого не ждёт.
- Репозиторий модели помечен `custom_code` и требует `trust_remote_code`; совместимость с
  vLLM обещана карточкой, но не проверена. **Это первое, что нужно проверить руками** — от
  неё зависит, доступен ли режим `prompt_mode: json` со structured output.

Имена параметров сверены с установленным клиентом (modal 1.5.5): `min_containers`,
`scaledown_window`, `modal.Cls.from_name`. В более ранних версиях они назывались иначе
(`keep_warm`, `container_idle_timeout`, `Cls.lookup`) — при обновлении клиента проверить
заново.

Порядок первого запуска важен: `modal deploy`, затем однократный `download_weights`, и
только потом инференс. Иначе веса поедут в том на первом же боевом вызове и холодный старт
съест бюджет ролика.

## Раскладка

```
back/
  app/
    main.py            сборка FastAPI, роутеры, CORS, обработчики ошибок
    api/v1/            videos.py jobs.py annotations.py export.py schema.py health.py
    schemas/           pydantic-модели — зеркало ../spec/openapi.yaml
    domain/            Segment / Annotation — перенос hyp0/schema.py
    services/          video_service, job_service, annotation_service, export_service
    repositories/      SQLAlchemy
    storage/           медиа и кэш кадров за интерфейсом
    events/            redis pub/sub → SSE
    config.py          pydantic-settings
  worker/
    main.py            цикл выборки задач, публикация прогресса
    stages/            submit · infer · parse · structure · postprocess · keyframe · persist
    modal_client.py    spawn / poll
  modal_app/
    marlin.py          Modal-приложение (деплоится отдельно)
  migrations/          alembic
  tests/
```

`domain/` — перенос `hyp0/schema.py` как есть, а не новая модель. Там уже написаны
проверка `end_s < start_s`, `boundaries(internal_only=…)` и канонический `text()`, и на
них уже опираются метрики. Своя параллельная модель означала бы два формата, которые
однажды разойдутся.

`storage/` держит файловое хранилище за интерфейсом: на сегодня это общий том `/data`,
завтра — S3, и подмена не должна расползаться по сервисам.

## Модель данных

```
videos      id · sha256(uniq) · filename · mime · duration_s · fps · width · height
            size_bytes · storage_path · created_at

jobs        id · video_id → videos · status · stage · progress · params(jsonb)
            model · structure_model · modal_call_id · raw_path
            timings(jsonb) · cost(jsonb) · error(jsonb)
            created_at · started_at · finished_at
            uniq (video_id, params_hash) частичный — под идемпотентность

annotations id · video_id → videos · job_id → jobs · version · model · meta(jsonb)
            created_at · updated_at

segments    id · annotation_id → annotations · index · start_s · end_s
            action · object · tool · confidence · keyframe_ts · edited_by_human
            uniq (annotation_id, index)
```

**Сегменты строками, а не jsonb-блобом.** `edited_by_human` — продуктовая метрика: она
отвечает на вопрос, какая доля автоматической разметки уходит без правок, то есть прямо
измеряет пользу системы. Считать её надо запросом по шагам, а не разбором json в
приложении.

**Непересечение шагов снимаем в базу.** Раз Postgres, пусть перекрытие будет невозможно
физически:

```sql
ALTER TABLE segments ADD CONSTRAINT segments_no_overlap
  EXCLUDE USING gist (
    annotation_id WITH =,
    numrange(start_s::numeric, end_s::numeric) WITH &&
  );
```

Требует `btree_gist`. Сервисный слой всё равно проверяет и отдаёт понятный `422` с кодом
`segment_overlap` — ограничение базы это последний рубеж, а не сообщение пользователю.

`annotations.version` — оптимистичная блокировка под `ETag` / `If-Match`. Истории версий
нет: это осознанное ограничение скоупа, а не забытая функция.

## Экспорт

Формат — канонический, из `hyp0/schema.py`, описан схемой
[`../spec/annotation.schema.json`](../spec/annotation.schema.json). Производные поля API
(`annotation_id`, `version`, `index`, `needs_review`) в выгрузку не попадают: смысл в том,
чтобы выгрузку можно было скормить `hyp0/metrics.py` без конвертера и мерить ровно то, что
уехало пользователю.

Валидация по схеме идёт **перед** отдачей. Не прошло — `500` с кодом
`export_schema_invalid` и списком нарушений, файла пользователь не получает. Требование
«100 % корректности формата» держится этой конструкцией, а не аккуратностью: невалидный
файл физически не может выйти наружу.

Схема отдаётся наружу (`GET /schema/annotation.json`), чтобы у потребителей была та же
копия, а не своя.

## Стоимость

Две графы в `jobs.cost`, обе — по факту прогона, а не оценкой. Это ровно те сервисы,
которые кейс требует назвать вместе со стоимостью обработки.

| Сервис | За что платим | Как считаем |
|---|---|---|
| Modal | GPU-секунды на `infer` | длительность вызова × тариф выбранной карты; тариф подставить из биллинга после первых прогонов |
| OpenRouter | стадия `structure` | `usage` из ответа; точную списанную сумму даёт их эндпоинт генерации по `generation_id`, его и пишем в `cost` |

Порядок величин для `structure`: около 550 входных и 320 выходных токенов на ролик. На
`anthropic/claude-haiku-4.5` ($1 / $5 за 1M — потокенная цена через OpenRouter совпадает
с прямой, сверено по их каталогу) это примерно **$0.002 за ролик**, то есть около **$2 за
тысячу**; кэш стабильного префикса снижает входную часть дальше. На
`anthropic/claude-sonnet-5` ($2 / $10) — вдвое больше.

Для разметки датасета целиком, где двухминутный бюджет на ролик не действует, у слагов
есть `:batch`-варианты вдвое дешевле. Интерактивному сценарию они не подходят, для тысячи
роликов — подходят.

Числа по Modal сюда не вписаны намеренно: тариф зависит от типа карты и от того, сколько
реально занимает инференс, а выдумывать их до первого замера — значит положить в защиту
цифру, которую нечем подтвердить.

## Конфигурация

Всё через переменные окружения, см. [`.env.example`](.env.example). Обязательные:
`DATABASE_URL`, `REDIS_URL`, `MEDIA_ROOT`, `MODAL_TOKEN_ID`, `MODAL_TOKEN_SECRET`,
`OPENROUTER_API_KEY`.

Ключи живут только в `.env`, который лежит в `.gitignore`. В репозиторий коммитится
`.env.example` с пустыми значениями.

Значения, которые задают поведение продукта, а не инфраструктуру, и потому подбираются
замером: `MARLIN_FPS` (2.0 — родная частота модели), `CONFIDENCE_THRESHOLD`,
`MIN_SEGMENT_S`, `MERGE_THRESHOLD`, `STRUCTURE_MODEL`.

Сервис не стартует с пустыми обязательными ключами: лучше упасть на старте, чем принять
ролик и упасть на стадии `structure`.

## Развёртывание

```bash
cp back/.env.example back/.env      # вписать ключи
modal deploy back/modal_app/marlin.py
docker compose -f back/docker-compose.yml up -d
```

Первое разворачивание Modal-приложения обязано пройти до подъёма стека: без него `api`
поднимется, но `GET /health` вернёт `ready: false`, и задачи приниматься не будут.

## Чего здесь осознанно нет

- **Аутентификации, ролей, биллинга** — вынесено кейсом. В спецификации это записано явно
  (`security: []`), чтобы читалось как решение, а не как пропуск.
- **Пакетной обработки.** Ролики по одному; очередь готова, но API загрузки пачкой нет.
- **Истории версий и отката.**
- **Горизонтального масштабирования.** Один воркер, одна очередь. Промышленная нагрузка
  вне скоупа, а один воркер делает время обработки измеримым.
- **Кэша ответов модели между роликами.** Дедупликация по sha256 закрывает практический
  случай — повторную загрузку того же файла на демо.
